# Secure QR Verification — Security Design

**Scope.** How a BUSTRAC HUB certificate is verified by a member of the
public, what the QR code actually contains, and what the design does and does
not protect against.

---

## 1. The problem with the previous QR code

Before this change the QR code on a Barangay Clearance or Certificate of
Indigency encoded the certificate's **CouchDB document id**:

```
http://<host>/verify?id=brgy_clearance_1788929049299_xx1y2z
```

Document ids in this system are **enumerable**. `CERT-<year>-<6 digits>`,
`brgy_clearance_<epochMs>_<random>` and `bus_clearance_<epochMs>_<random>`
all follow a predictable shape, and the public verification endpoint accepted
any id that matched a known prefix. That means:

* anyone could walk the id space and ask the server about other people's
  certificates;
* a certificate number, a resident id, a name or a birth date could be
  **guessed** into a QR code and presented as if it were genuine;
* nothing bound a QR code to the document it claimed to represent.

A QR code is a *pointer*, not a *proof*. Uniqueness of the id is not
authenticity of the document.

---

## 2. What the QR code contains now

```
https://<host>/verify?token=<43-character base64url secret>
```

The token is a **256-bit cryptographically random secret** generated by the
server (`crypto.randomBytes(32)`, `server/utils/verificationTokens.js`). It is
derived from nothing — not from the certificate number, the resident id, a
name, a birth date or a timestamp — so it cannot be derived, guessed or
enumerated.

| Property | Implementation |
| -------- | -------------- |
| Entropy | 256 bits, `crypto.randomBytes` (server-side only) |
| Encoding | base64url, 43 characters, URL-safe, no padding |
| Storage | **Only the SHA-256 hash is stored.** The raw token exists once, in the response to the minting request, and afterwards only on the issuing device (inside the certificate document, so a reprint can reuse it) |
| Lookup | The verification record's document id **is** the token hash, so a lookup is a single `db.get()` — no index, no query, and no field that could leak the secret through a view or a Mango selector |
| Uniqueness | Two different tokens cannot produce the same document id. The minting endpoint also handles a (astronomically unlikely) 409 by minting a fresh token |
| Binding | The record names exactly one `certificateId`. The endpoint always reports the certificate the record is bound to |

### The server owns the registry

Two server-owned document types are created (both are refused by the sync
proxy, so a device can never write them — see
`server/index.js`, `SERVER_OWNED_DOC_PREFIX`):

| Document id | Type | Purpose |
| ----------- | ---- | ------- |
| `certverify_<sha256(token)>` | `certificate_verification` | The record a token resolves to: `certificateId`, `certificateType`, `certificateNumber`, `issuedAt`, `status`, `revokedAt`, `revokedBy`, `reprintCount`, `tokenHash` |
| `certverify_cert_<sha256(certificateId)>` | `certificate_verification_index` | An alias from a certificate to its token hash, so a revocation or a re-mint can find the record **without** a database-wide scan and without a Mango index |

## 3. The endpoints

| Method | Path | Access | Purpose |
| ------ | ---- | ------ | ------- |
| `POST` | `/api/certificates/verification-token` | `admin`, `staff` | Mint (or reuse) the verification token for an issued certificate. Returns the raw token **once** |
| `POST` | `/api/certificates/revoke` | `admin`, `staff` | Revoke a certificate and its verification record |
| `GET` | `/api/certificates/verify-token/:token` | **public**, rate limited | Verify a certificate by its secure token |
| `GET` | `/api/certificates/verify/:id` | **public** | The **legacy** document-id verification, kept so certificates printed before this change still verify |

### Minting rules

A token is issued **only** when the certificate is genuinely issued. The
server reuses the existing status policy (`server/utils/verifyStatus.js`) —
the same module that backs the public endpoint — so a document must have an
issued-like status **and** reliable issuance evidence (a real reference number
and a real issue date). A `Pending`, `Submitted`, `Under Review`,
`Awaiting Approval`, `Draft`, `Cancelled` or `Needs Revision` record is
refused with `409` and receives no token.

### Revocation

`POST /api/certificates/revoke`:

1. sets the verification record to `status: 'revoked'` — this is the
   **authoritative** public signal, because the record is server-owned and no
   replication race can resurrect it;
2. best-effort sets the certificate document's own `status` to `'Revoked'`
   (the device owns that document, so a later replication may overwrite it —
   which is precisely why the verification record is the authority);
3. writes an `audit_log` entry with action `REVOKE_CERTIFICATE`, the actor,
   the timestamp and the certificate reference.

A revoked certificate can never be re-minted; a replacement is a **new
document** with a new id and a new token.

### Rate limiting

The public token endpoint is throttled to **30 requests per minute per client
address** (`server/utils/rateLimit.js`, a small dependency-free fixed-window
limiter — the project has no rate-limiting dependency and adding one would
require an install in every deployment).

**Known limitations of the limiter:** the counters live in the process memory,
so a restart clears them and a multi-process deployment gets one window per
process. A shared store would be required for a cluster. The window is fixed
rather than sliding, so a caller can burst twice the limit across a window
boundary.

The token is **never logged in full**. The controller logs only the failure
message; the raw token appears in exactly one place — the minting response.

## 4. The public verification page

`frontend/src/pages/VerifyDocument.tsx` now accepts `?token=` in addition to
the legacy `?id=`.

| Server answer | Page result |
| ------------- | ----------- |
| `valid` | **Valid** — "Document Verified" |
| `invalid` (revoked / cancelled / voided …) | **Revoked** — "Document Revoked / Invalid" |
| `expired` | **Expired** — "Document Expired" |
| `404` | **Not Found** — "Document not found in the barangay records" |
| network failure / 5xx / 429 | **Unable to Verify** — amber, explicitly *not* a red "invalid" verdict |

**The token path never falls back to the local PouchDB.** A token can only be
resolved by the authoritative server; letting a local record answer would
mean an unsynchronised certificate could be reported as verified. An offline
reader is told *"An offline result is never a confirmed result."*

### What the response reveals

Exactly seven fields, and nothing else:

```json
{
  "valid": true,
  "status": "valid",
  "statusLabel": "Authentic & Valid",
  "documentType": "Barangay Clearance",
  "referenceNo": "BC-2026-0001",
  "issuedTo": "JUAN DELA CRUZ",
  "dateIssued": "September 15, 2026"
}
```

No address, no contact number, no birth date, no purpose, no OR number, no
purok, no signature, no resident record, and **never the token itself**. The
`issuedTo` name is retained because comparing it against the physical
document is exactly what detects a copied QR code; everything else that is not
needed for that comparison is withheld. A test asserts the response contains
no address, no contact number, no purpose, no OR number and no purok.

The page is a single responsive card with large tap targets and no
desktop-only layout, so it works on a phone at the counter.

## 5. What happens when a QR code is copied

**A copied QR code cannot be prevented.** The token is a bearer secret printed
on the document; anyone who photographs it can present it. No design based on
a printed QR can stop that, and this system does not claim it can.

What the design *does* guarantee is that a copied QR code **cannot silently
pass as the document it was pasted onto**:

* the token resolves to **one** certificate, and the page always shows that
  certificate's type, reference number, issue date and name;
* a verifier who compares those four fields with the physical document sees
  the mismatch — a clearance number that does not match the paper, a name that
  does not match, an issue date that does not match;
* the response is deliberately minimal precisely so that comparing it with the
  paper is practical.

**Scanning does not invalidate anything.** There is no one-time-use QR: a
legitimate certificate is checked many times (a business asks for it twice, a
barangay official re-checks it), and the record is never consumed by a scan.
`status` stays `active` and `reprintCount` is not incremented by a scan.

**Automatic invalidation after the first scan was deliberately not
implemented.** It would break legitimate re-checking and there is no
documented business requirement for it. A one-time-use QR would need an
explicit decision from the barangay, and would need the scan to be recorded
server-side, which raises the privacy and data-minimisation questions the
current design avoids.

### A printed digital signature?

A short human-verifiable signature (for example a truncated HMAC printed
under the QR) was considered and **not** implemented. The reasons:

* it would need a key that the browser can use for signing but cannot read,
  and the browser has no such primitive that is portable across the browsers
  in use here;
* a signature that the public page can check is, in practice, a second copy of
  the same bearer secret in a shorter, weaker form — it would be easier to
  copy and easier to brute-force than the full token, and it would add a
  second thing to get wrong;
* it adds no verification power the server-side token does not already
  provide, because the authoritative check is the server round trip anyway.

If the barangay later requires an offline, no-network way to check a
certificate, the honest answer is a **detached, signed credential** (a
short-lived signed code verified with a published public key, plus an online
check), not a static printed signature. That is a separate design decision
and is not implemented here.

## 6. Revocation, reprinting and the audit trail

| Event | Effect | Audit entry |
| ----- | ------ | ------------ |
| Issue | A token is minted and stored server-side; the raw token is written onto the certificate document by the device | `ISSUE_CERTIFICATE_VERIFICATION_TOKEN` (server) and `ISSUE_CERTIFICATE` (device) |
| Revoke | The verification record becomes `revoked`; the certificate document is best-effort marked `Revoked` | `REVOKE_CERTIFICATE` (server) |
| Reprint | The device presents the token it already holds, so the **same** token is returned and the same QR is reprinted. No second identity, and the original is not invalidated | `REPRINT_CERTIFICATE` (device) |
| Scan | Nothing changes. The record is read-only | none (a scan is not an administrative action, and logging every public scan would create a large, linkable log of who checked what) |

The server-side audit documents are written into the shared database as
`type: 'audit_log'` with `action`, `module: 'CERTIFICATES'`, `actor`
(`{ username, role, residentId }`), `recordId`, `details`, `timestamp` and
`createdAt`, so they appear in the existing **Audit Log** view of the
administrator portal.

**Reprinting and the device copy of the token.** The raw token is stored on
the certificate document so a reprint can reuse it. That document is owned by
the device, so the token is present in the shared database and replicated to
other staff devices. This does not weaken the design: the token only ever
proves that **one** certificate is valid, it cannot be used to create a
different certificate, and a forged document carrying someone else's token
still resolves to that other certificate (and fails the comparison against
the physical paper).

## 7. Offline-first behaviour

BUSTRAC HUB is offline-first: certificates are written to the local PouchDB
and replicated to the server later. The rules that follow from that:

1. **A certificate issued offline cannot obtain a token.** There is no server
   to mint it. The certificate is issued **without** a verification QR, and
   the issuance path reports the token as *pending*.
2. **An unsynchronised certificate is never reported as verified.** The public
   endpoint only knows about documents the server has actually received, so an
   offline-issued certificate verifies as **Not Found** until it replicates.
   This is the honest answer: the barangay has not received it yet.
3. **The token path never falls back to the local database.** A local record
   must not be able to make a certificate look publicly verified.
4. **A token is minted only after the certificate has been written and
   marked as issued**, so a draft, a pending request and a rejected request can
   never be given one.
5. **The verification registry is server-owned**, so a device that replicates
   later cannot overwrite a revocation or forge a verification record: the
   sync proxy refuses client writes to `certverify_*` documents.

### What an administrator should do

* **Before** the certificate is needed, the issuing device must be online at
  least once so the certificate replicates and the token is minted.
* If a certificate was issued offline, open the issuance screen again once
  the device is online — the token is then minted and the certificate can be
  reprinted with a working QR.
* The printed QR is the authority. If a document has no QR, or the QR does
  not open, treat the document as **not verifiable** and contact the
  barangay.

## 8. What the certificate status pinning closes

**The finding.** The sync proxy pinned lifecycle fields for blotter records and
event registrations, but **not** for certificates: a resident could write their
own `certificate_request` with `status: 'Issued'` and/or `isIssued: true`
(plus a plausible reference number and issue date). The legacy `GET
/api/certificates/verify/:id` endpoint resolves the status from the document
itself, so it would report that resident-forged document as *Authentic &
Valid*. The token endpoint was never the weak point — a verification record can
only be minted by admin/staff and lives under the server-owned `certverify_*`
prefix, which the proxy refuses for every client — but the id endpoint had
nothing to check against.

**What changed** (`server/utils/syncAuthorization.js`):

* `RESIDENT_PROTECTED_CERTIFICATE_FIELDS` — `status`, `step`, `isIssued`,
  `issuedAt`, `issuedBy`, `approvedBy`, `approvedAt`, `releasedAt`,
  `releasedBy`, `rejectionReason`, `revokedAt`, `revokedBy`,
  `verificationToken` — is compared field by field against the stored
  document for `certificate_request`, `barangay_clearance` and
  `business_clearance`. Any difference denies the write with
  `certificate lifecycle field not writable by residents`. Absent on both
  sides means "no change" and is allowed; only an admin/staff session may
  advance the lifecycle.
* A **new** certificate document must start in its initial, unissued state —
  `status` `Pending`/`Submitted`, `step` `Submitted`/`1`, never `isIssued`.
  Anything else denies the create with `certificate must start in
  Pending/Submitted state`.

Residents can still **file** a request (`certificate_request` remains in
`RESIDENT_WRITE_TYPES`) and edit its non-lifecycle fields such as `purpose`
and `remarks`; only the barangay can issue it. Staff writes are unaffected:
admin/staff bypass this module entirely (`authorizeSyncAccess` in
`server/index.js`), and the pinning itself is resident-only.

**Defence in depth on the read side.** The public token endpoint never trusts
the document's claim alone: it re-checks the certificate server-side with
`resolveDocumentStatus` (`server/utils/verifyStatus.js`) and answers `404 Not
Found` for any token with no server-owned verification record behind it — a
forged document therefore has nothing to be verified *by*. Together with the
write-side pin, the two paths to a forged "Authentic & Valid" answer are
closed: the document can no longer be written, and the registry that vouches
for it can no longer be populated by a resident.

Covered by `server/test/syncAuthorization.test.js` (certificate lifecycle
pinning cases) and `server/test/certificateVerification.test.js` (case 13: a
resident-forged certificate with no verification record is not found by
token).

## 10. Remaining risks

* **A printed QR is a bearer token.** It can be photographed. The system
  detects the mismatch against the paper; it cannot prevent the copy.
* **The rate limiter is per process and in memory.** A restart resets it, and
  a multi-process deployment multiplies the effective limit.
* **The certificate document carries the raw token** so a reprint can reuse
  it. Anyone with read access to the shared database can read it. It still
  only ever proves one specific certificate.
* **The public endpoint is unauthenticated by necessity** — the whole point
  is that a member of the public can check. It is throttled and answers
  neutrally, but it is still a public oracle for "does this token exist".
* **The legacy `?id=` endpoint still exists** for certificates printed
  before this change. It is document-id based and therefore enumerable; it
  should be retired once the paper stock has been reissued.
* **No expiry of the token itself.** A token remains valid for as long as its
  certificate is valid, and the certificate's own expiry is what governs it.
* **HTTPS is still required in production** and is not enforced by the
  application.
